# P0 修复报告：工具调用协议文本当正文泄漏（DSML 假装调用）

日期：2026-09-21 ｜ 提交：本次 ｜ 涉及文件：`render-api/server.js`、2 个合约测试更新、新增 1 个合约测试

## 现象（用户截图实证）

模型在**正文**里输出大段内部纠结过程（"我应该尝试调用 search_social……让我试着调用一下"），最后把
`<| | DSML | | invoke name="search_social">` **协议原文原样打印**，工具从未真正执行。
模型自述："系统提示的工作模式部分提到 search_social 等工具，但实际可用的工具列表只有 6 个。"

## 根因链（四层叠加）

| # | 根因 | 后果 |
|---|---|---|
| 1 | `callDeepSeekViaResponses` 内 `var allowToolsWithThinking = workModeEnabled;` 引用了**未定义变量**（它只是请求处理器的局部变量） | 每次进入工具轮循环即 ReferenceError → **所有 Responses 路径调用（内置搜索/工作模式/深度研究）整体瘫痪**，上层 catch 后报"AI 调用失败" |
| 2 | Responses 路径 `(useThinking && !workModeEnabled) ? [] : …` 思考模式清空 tools，但 system prompt **无条件宣称**"可用工具（…）" | 提示词承诺 ≢ 实际下发，模型"被承诺有工具却拿不到" |
| 3 | 工作模式 + 思考 + 搜索开关关 → `useBuiltInSearch=false` → 落到标准路径；标准路径 `needsFcCheck` 要求 `!useThinking` | 全程**零工具裸跑** |
| 4 | 标准路径思考模式：prompt 宣称工具 + 实际无工具 | 模型只能拿 DSML 文本"假装调用"，正文实时流式推送**无法拦截** → 原文泄漏 |

## 修复（render-api/server.js）

1. **ReferenceError 修复**：`allowToolsWithThinking = true`（/responses 实测 thinking(effort=none/low/high/max) 与 tools 可共存；调用方传入的 tools 一律下发；上游拒绝时已有 effort:none 自动降级重试兜底）。
2. **Responses 路径思考模式不再清空工具**：`responsesTools = workModeEnabled ? aiToolsForWorkMode() : aiToolsForSearch(...)`，`tool_choice` 恒为 `'auto'` —— 宣称 ≡ 下发。
3. **工作模式强制走 Responses**（视觉直传除外，避免多模态数组被 String() 毁坏）：`useBuiltInSearch = (workModeEnabled && !_visionEngaged) || (原条件)`，模型归一到 `DEEPSEEK_RESPONSES_MODEL`。Responses 路径自带 DSML 解析 + 内容缓冲（deferToolRoundContent），协议文本不可能再漏到前端。
4. **标准路径思考模式如实口径**：进入标准路径且思考开启时，把 prompt 中"可用工具（…）"整句改写为"本次请求未挂载任何工具：不要尝试调用任何工具，也不要输出任何工具调用协议文本"——从根上掐掉模型假装调用的动机。
5. **FC 预检兜底**：工作模式行去掉 `!useThinking`（视觉直传等工作模式仍走标准路径的场景的最后一道工具挂载防线）。
