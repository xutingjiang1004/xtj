## 一、问题 1：内置 Flash 模型无法使用（Pro 正常）

### 症状
- 选择内置 `deepseek-v4.1-flash` 时前端提示「使用失败」，但 DeepSeek 账户余额充足。
- 选择 Pro 模型一切正常。

### 排查过程（先证伪再定位）
最初怀疑是 `render.yaml` 里的模型别名 `deepseek-v4-flash-vision-exp` 配错。
**实测证伪**：直接调用 `getPreferredDeepSeekModel()`，所有场景都正确返回
`deepseek-flash`；且官方文档确认 `deepseek-flash` 是有效模型名。

### 真正根因（路由分裂）
```js
// 修复前（server.js 约 21423 行）
var useBuiltInSearch = (webSearchPref === false && validatedModel === DEEPSEEK_RESPONSES_MODEL);
```
常量关系：
```js
DEEPSEEK_RESPONSES_MODEL === DEEPSEEK_MODEL_FLASH === 'deepseek-flash'
```
因此 `validatedModel === DEEPSEEK_RESPONSES_MODEL` 在**选中 Flash 时恒为 true**，
于是「选 Flash」被无条件强制走 Responses 路径；「选 Pro」因名字不等而默认走
Chat Completions（正常）。

两条链路的健壮性差异 → 表现为「Pro 能用、Flash 不能用」的分裂。

### 修复
把「模型名」与「是否走内置搜索」两个正交概念解耦：

```js
var useBuiltInSearch = _webSearchForceResponses && (
    (webSearchPref === true)
    || (!thirdPartySearchOk && proactiveSearch)
    || (proactiveSearch && (explicitSearchIntent || liveInfoIntent) && webSearchPref !== false)
);
```

现在是否走 Responses 只由「用户是否开了网页搜索 / 是否有明确搜索意图」决定，
与用户选了哪个模型无关。同时补了路由日志：

```
[AGENT-STREAM] route=%s model=%s web_search=%s proactive=%s thirdPartyOk=%s
```

### 附带加固
`getPreferredDeepSeekModel()`（约 204 行）：模型探测失败（`availableSet` 为空，
例如 key 缺失或探测超时）时，不再盲目把 `normalized` 发给上游，
改为优先使用 `process.env.DEEPSEEK_MODEL` 显式配置，再退回常量。

## 二、问题 2：内置模型回复时显示「AI 连接中断，请稍后重试」

### 根因
本路由所有错误出口都是「发一个 `error` 事件 → 直接 `safeEnd()`」，
**从不发送 `type:'done'` 终结事件**。

前端据此判定 `doneReceived` 仍为 `false`，在 `error` 事件处理完成后的收尾
判断链里落入 `!doneReceived` 兜底分支，用笼统的「AI 连接中断」覆盖掉
服务端刚刚给出的真实错误原因。

### 修复（前后端配合）

**后端** — 新增 `terminateWithError(errObj)`（`safeEnd` 之前定义）：
补发终结 `done` 事件，并带 `_terminalSent` 幂等标志防重复：

```js
{ complete: false, interrupted: false,
  finish_reason: 'upstream_error', terminal_error: true }
```

所有错误出口由 `writeSse(...error) + return safeEnd()` 改为
`return terminateWithError({...})`，共 14 处（上游 400 / 流内超时 / 流意外结束）。
4xx 分支额外拼接上游原始错误：`（上游：' + errMsg + '）`。

**前端** — `js/ai-agent.js`：
- 新增 `terminalErrorSeen` / `lastServerError` 两个状态位；
- `error` 事件分支置 `terminalErrorSeen = true; evtHandled = true;` 并记录真实文案；
- 收尾判断链新增优先分支：
  ```js
  } else if (terminalErrorSeen) {
    cleanupRenderers();
  } else if (!doneReceived) {
  ```

效果：服务端已明确告知的失败显示**真实原因**；只有连接真的意外断开才提示
「AI 连接中断」。

## 三、优化：AI 调用工具的多样性 / 速度 / 流畅性

### 3.1 多样性 — 工具可见性与提示词不一致（最高价值）

**问题**：`aiToolsForSearch()` 无条件剔除 `search_web`，注释理由是
「避免与内置搜索重复」。但该理由只在走 Responses 内置 `web_search` 时成立；
非工作模式 + 开搜索走的是 Chat Completions 兼容路径，**根本不存在内置
web_search**，`search_web` 是唯一原生搜索工具。

而系统提示词 `buildCatAiToolSummary(true)` 是**从全量 `AI_TOOLS` 动态生成**的，
会向模型宣称「你有 search_web」。**提示词说有、下发的 tools 数组没有** ——
这正是模型幻觉能力、自述工具数不对的经典成因。

**修复**：`aiToolsForSearch` 只按 `includeTavily` 裁剪 `tavily_search`
（它才是真正与内置搜索重复、且受第三方配额约束的那个），`search_web` 恒可见。

### 3.2 速度

| 项 | 修复前 | 修复后 | 理由 |
|---|---|---|---|
| Tavily 预搜注入等待 | 6000ms | **2500ms** | 实测 P50≈1.2s / P90≈2.2s；超时不失败，后台继续跑，工具可兜底 |
| Tavily 收尾 `await` | 无上限 | **1200ms** | 防止个别卡死请求把已生成好的整段回复扣住 |
| `FIRST_TOKEN_TIMEOUT_MS` | 90s / 60s | **60s / 45s** | 正常请求零影响，异常请求失效判定提前一倍 |
| `SINGLE_TOOL_TIMEOUT_MS` | 45s | **20s** | 工具内部已各自带 8~15s 超时；正常工具 P99<10s，仍留一倍余量 |

### 3.3 流畅性

**问题**：工具执行期（并行 N 个 `read_web_page` / `run_code` / 多路搜索，
可达数秒~20s）SSE 无任何事件 → 前端「正在使用工具…」长时间静止，
用户以为卡死并重发；极端情况空闲连接被代理切断。

**修复**：
1. **后端**：两处工具执行段（Responses 路径 + 标准流式路径）新增
   `setInterval` 每 3s 推送 `tool_progress` 事件，`Promise.all` 完成后
   `clearInterval`。
2. **前端**：新增 `tool_progress` 分支，原地把运行中步骤状态改写为
   `进行中 · 已 12s`（`toolProgressTick` 计数），既保活又给出真实进展感。
3. **前端**：工具全部返回后补一条「整理检索结果并作答 / 进行中」占位步骤，
   消除「完成态静止但其实还在生成」的误解；正文首个 `content` 到达时
   自动收敛为 ✍️ 完成态（保留不删除，维持时间线叙事完整）。

### 3.4 少绕路 — 工具结果上限

| 位置 | 修复前 | 修复后 |
|---|---|---|
| Chat 路径 `max_tool_result_chars` 默认 | 8000 | **24000** |
| Responses 路径 `toolContent` slice | 8000 | **24000** |

`read_web_page` / `read_document` / `run_code` 的实际输出常远超 8000 字符，
被腰斩后模型只能「再读一次」或凭残缺片段作答 —— 既多一轮工具往返（拖慢
速度）又降低准确率，还会因「信息不足」反复换工具（表现为乱调工具）。
24000 字符约 8k tokens，远低于 prompt 总量硬上限，`clampPromptTotal` 处另有兜底。
