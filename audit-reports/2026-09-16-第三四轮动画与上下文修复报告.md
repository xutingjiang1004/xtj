## 一、第三轮：回复动画流畅性（SSE 合并 + 渲染提速 + 视觉动效）

### 1.1 服务端：SSE 小包合并

**问题**：DeepSeek 上游逐 token 回传，后端逐 token 转发。一次长回复可产生数千个 SSE 事件，每个事件都有完整的 `data: {...}\n\n` 封装与网络往返开销。前端被高频小包淹没，`requestAnimationFrame` 每帧只能消费一小部分，积压导致文字"一顿一顿"地吐。

**修复**（`render-api/server.js`）：新增 40ms 合并窗口。

```js
var SSE_COALESCE_MS = 40;
var contentCoalesceBuf = '';   var contentCoalesceTimer = null;
var reasoningCoalesceBuf = ''; var reasoningCoalesceTimer = null;
function flushContentCoalesce() { /* 合并写出单个 content 事件 */ }
function flushReasoningCoalesce() { /* 合并写出单个 reasoning 事件 */ }
function scheduleContentCoalesce() { /* 延迟 flush，带 timer 复用 */ }
function scheduleReasoningCoalesce() { /* 同上 */ }
```

- 正文累积到 **240 字符** 立即刷出，否则等 40ms 窗口到期。
- 思考过程累积到 **160 字符** 立即刷出。
- 流循环退出后强制 `flushContentCoalesce(); flushReasoningCoalesce();` 保证不丢尾。
- `safeEnd()` 内清理两个 timer，避免悬挂定时器。

**收益**：实测事件数压缩 **105 倍**，且内容拼接后与原始 token 流 **byte-identical**（`/tmp/verify/coalesce_test.js` 验证）。

### 1.2 前端：流式渲染预算算法

**问题**：原预算固定偏小，积压 80+ 字符时每帧只放 12~24 字符，追赶速度跟不上到达速度，积压越滚越大 → 视觉上"越到后面越慢"。

**修复**（`js/ai-agent.js` + `js/ai-core/stream-renderer.js` 同步）：

```js
var baseBudget = Math.max(12, Math.floor(budget || 24));
if (pending.length > 64)      baseBudget = Math.max(baseBudget, Math.floor(pending.length * 0.62));
else if (pending.length > 32) baseBudget = Math.max(baseBudget, Math.floor(pending.length * 0.40));
else if (pending.length > 12) baseBudget = Math.max(baseBudget, 18);
if (pending.length / baseBudget > 3) baseBudget = Math.floor(pending.length / 3);
```

**收益**：积压 80+ 时单帧吞吐提升 **+25 ~ +136 字符**，同时保留 `maxChunk` 自然断点切分（不把英文单词从中劈开）。

### 1.3 前端：Markdown 节流自适应

原固定 200ms 节流，长文渲染滞后感明显。改为 **600 字符以内 90ms / 以上 140ms**，短回复更跟手，长回复不过度重排。

## 二、第四轮：内置模型上下文丢失修复

### 2.1 根因

两条链路的上下文来源**完全不对称**：

| 链路 | 端点 | 上下文来源 | 可靠性 |
|---|---|---|---|
| 第三方 API 模型 | `/custom-chat/stream` | 前端请求体显式带完整历史数组 | ✅ 稳定 |
| **内置模型（Flash/Pro）** | `/chat/stream` | 服务端 `loadAiContext()` 查 Supabase 还原 | ❌ 单点脆弱 |

内置链路前端**只发当前 message + conversation_id**，服务端靠 `convId` 查库。一旦 `convId` 丢失 / 被重置 / 查询失败，历史就**静默变空**——用户感知就是"上一秒说的下一秒就忘、每条对话都是独立的"。

已验证 `req.body.messages` 在主路径 **零引用**（`grep` 返回空），即前端即使发了历史服务端也完全忽略。

### 2.2 修复

**服务端**（`render-api/server.js`）：`loadAiContext` 新增第三参数 `clientHistory`，**优先使用客户端传入的历史**，查库降级为回退路径。

```js
async function loadAiContext(userName, convId, clientHistory) {
  var ctx = { history: [] };
  if (Array.isArray(clientHistory) && clientHistory.length > 0) {
    for (var chi = 0; chi < clientHistory.length; chi++) {
      var ch = clientHistory[chi];
      var chRole = String(ch.role || '');
      if (chRole !== 'user' && chRole !== 'assistant') continue;
      var chContent = String(ch.content == null ? '' : ch.content);
      if (!chContent.trim()) continue;
      ctx.history.push({ role: chRole, content: chContent.slice(0, AI_CHAT_HISTORY_MSG_MAX_CHARS) });
    }
    console.log('[AGENT-CHAT] ctx from client: user=%s conv=%s history=%d', ...);
    if (ctx.history.length > 0) return ctx;
  }
  // ↓ 原查库逻辑作为回退
}
```

调用点（`server.js:21251`）：

```js
var ctxPromise = loadAiContext(userName, convId, req.body && req.body.messages);
```

**前端**（`js/ai-agent.js:7897`）：内置链路请求体新增 `messages` 字段，与第三方链路完全对齐（复用同一套裁剪策略）：

```js
var _builtinHist = [];
// ... 按 CONTEXT_LIMIT_MAX / NORMAL 截取轮数，按 MSG_MAX_CHARS_MAX / NORMAL 截字符
messages: _builtinHist.length ? _builtinHist : undefined,
```

**收益**：内置模型的上下文来源与第三方模型**同源同策略**，不再依赖单点数据库链路；断网/DB 抖动时仍能从请求体拿到历史。

## 三、第四轮：工具调用紧凑轮次动画

### 3.1 根因

旧实现每个工具建 **四行完整卡片**（图标 + 标题 + 状态 + 详情）。并行调用 5 个工具 = **20 行**，且全部展开平铺。更糟的是 `tool_pending` 会为同一工具**再建一条独立步骤**——用户截图里"准备工具 / 联网检索 / 社媒检索"重复出现即源于此。同时没有"轮次"概念，多轮工具调用全部平铺堆积。

### 3.2 修复：引入"轮次"容器

**一个轮次 = 一次 `tool_calls` 事件产生的并行工具集合。**

新增两个函数（`js/ai-agent.js:2330` / `2374`）：

```js
// 依据子条目状态刷新轮次摘要行
function updateToolRoundState(roundBox) {
  // 统计 is-done / is-error
  // settled → 移除 is-running、加 is-done、图标 ⏳→✅/⚠️、
  //           摘要行改为「已完成 N 个工具」
  // 未完成 → 摘要行「并行调用 N 个工具」+ 计数「x/y 完成」
}
function refreshOwningToolRound(stepEl) { /* 找到所属轮次并刷新 */ }
function forceSettleToolRound(roundBox)  { /* 终态强制收敛，停掉所有跳动动画 */ }
```

**五个事件分支全部重写**：

| 事件 | 旧行为 | 新行为 |
|---|---|---|
| `tool_calls` | 每个工具 4 行卡片 | 创建 `.ai-tool-round`（摘要行 + 紧凑列表），**全局按 stepId 去重**，状态文案"搜索中" |
| `tool_pending` | 再建一条独立步骤（重复源） | 复用同名条目 / 复用运行中轮次，**消除重复** |
| `tool_result` | 无差别把其他并行工具也标完成 | 只收敛自己（`refreshOwningToolRound`），状态文案"已完成" |
| `tool_error` | 新增失败条目 | 优先就地转失败态，不新增条目 |
| `tool_progress` | 无 | 文案「搜索中 · 已 12s」+ 刷新所有轮次计数 |

### 3.3 视觉效果（对齐用户诉求）

用户要求："*并行搜索五个网页或工具，直接显示五个正在搜索中，全部搜索完之后就把搜索中那些字和图标换成已完成*"

- **运行中**：摘要行 `⏳ 并行调用 5 个工具 · 2/5 完成`，条目各自 `🔍 搜索中`
- **全部完成**：摘要行 `✅ 已完成 5 个工具`，条目图标 `🔍 → ✅`、文字 `搜索中 → 已完成`，整轮加 `is-done` 停掉动画
- **继续搜索**：新 `tool_calls` 事件开新轮次，回到"搜索中"态
- **部分失败**：摘要行 `⚠️ 5 个工具已完成（1 个失败）`

### 3.4 收尾收敛（关键补充）

`clearAssistantTransientStatus` 原本只处理 `.ai-tool-step.is-running`，**不处理新增的 `.ai-tool-round.is-running`**。若不补，中断/超时后摘要行会永久停留"并行调用 N 个工具 · 2/5 完成"，图标一直是 ⏳。

已补：

```js
try {
  var _runningRounds = target.querySelectorAll('.ai-tool-round.is-running');
  for (var _rr = 0; _rr < _runningRounds.length; _rr++) forceSettleToolRound(_runningRounds[_rr]);
} catch (eSettleRound) {}
```

同时把步骤收敛文案由「已结束」统一为「已完成」并补 `✅` 图标。

### 3.5 CSS（`css/ui-enhance.css`）

新增 `.ai-tool-round` / `.ai-tool-round-head` / `.ai-tool-round-icon` / `.ai-tool-round-label` / `.ai-tool-round-count` / `.ai-tool-round-list` 紧凑轮次样式：

- `.ai-tool-round-list .ai-tool-step` 单行紧凑布局（`align-items: baseline`，`gap: 6px`）
- `@keyframes xtjToolIconBreath`（1.6s opacity 呼吸，取代原光晕避免糊成一团）
